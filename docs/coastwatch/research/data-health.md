## 1. Source health and data quality matrix

Shared mechanics, which apply to every source:
- **HTTP**: `fetch()` defaults to a 90 s socket timeout, 240 s per download, 3 retries, and 5/10/20 s exponential backoff (`P:http.py:92-141`). 4xx responses are not retried, except **403 and 429, which are retried** (`http.py:121-132`).
- **Circuit breaker**: per dataset (host + path), it opens after 2 consecutive failed fetches. Each of those already includes the retries. A host is skipped after 2 consecutive hangs. A 404 does not count toward either (`http.py:150-214`). Each run creates a new breaker, so nothing persists between runs.
- **Time budgets**: per source (`P:pipeline.py:93-103`) plus 25 min for the whole run (`pipeline.py:104`). The job limit is 40 min (`.github/workflows/coastwatch-data.yml:38`).
- **Failure policy**: when a source fails, its previous layers and artifacts are re-emitted with their own dates. `_failed()` copies `last_success_at`, `latest_issued_date` and `latest_valid_date` from the previous status and sets `outcome="failed"` with the error (`pipeline.py:1-9, 475-487`). A pipeline run itself is never blocked by one source.
- **Alerting** (production channel only):
  - The `notify-health` issue is driven by `P:health.py` (`coastwatch-data.yml:122-150`). A failing NOAA source alerts after **3 consecutive failed runs** (`health.py:36,69-72`). Only `charm`, `satellite_chl` and `hf_radar` are covered (`health.py:43`).
  - The `notify-failure` issue covers a failed or cancelled workflow, deduplicated to one comment per 24 h (`yml:152-209`). `notify-recovered` closes it again (`yml:211-230`).
  - The `notify-review` issue covers official-page changes (`yml:104-120`).
- **Verification**: the C-HARM, satellite and currents data are re-read from ERDDAP after the run (`yml:71-79`). The step is skipped when that source did not update (`P:cli.py:46-52,83-87,104-108`). The verifier's own fetch uses `retries=4` and no breaker (`P:verify.py:59`). A fetch error in that step fails the whole build, so **nothing is published for any source**, including healthy ones.

## 3. Why the Ocean Map forecast panel showed "Current · issued 1 day ago" and "Last update failed (Oct 12, 5:42 PM PDT); showing the last successful run"

Both statements are true, but they are computed from different inputs. Nothing reconciles them.

1. **What the failure line reports.** Run 38328551760 started at 00:42:15Z on Oct 13, which is **5:42 PM PDT on Oct 12**. Every C-HARM probe got HTTP 403 from `coastwatch.pfeg.noaa.gov`, so `charm.run()` returned no layers. `pipeline.py:169-173` then re-emitted the 15:29Z run's layers and the `forecast_runs` entry, and wrote a status with `outcome:"failed"` and `last_attempt_at: 2026-10-13T00:42:33Z`. `_failed()` (`pipeline.py:475-487`) copied the previous `last_success_at` (15:29Z) and dates. `LayerDock.tsx:317` prints that `last_attempt_at` in Pacific time: "Last update failed (Oct 12, 5:42 PM PDT); showing the last successful run".
2. **What the badge reports.** `ForecastSection` classifies the *layer* (`LayerDock.tsx:241-242` → `classifyTime` → `freshness.ts:34-42`) using `basis: issued_date`. The issued date is **2026-10-11**, and it is *derived* (nowcast valid 10-10 + 1). The age is computed against **Pacific today**, 2026-10-12 (`freshness.ts:21-25`), so age = 1. `current_max_age_days` is 1, so the state is "current". The `FreshnessBadge` renders "Current · issued 1 day ago" (`Badges.tsx:30,44-48`, `W:lib/time.ts:49-53`). The badge never looks at `charmStatus.outcome`.
3. **Why this is misleading rather than just two facts side by side:**
   - The policy note published with the data says "Current: issued today or yesterday **(UTC)**" (`charm.py:119`), and `health.py:75,90` uses UTC. At 00:42Z it was already Oct 13 UTC, so by the pipeline's own rule the run was 2 days old, which is **Stale**. The web's Pacific calendar (a deliberate choice, `freshness.ts:18-20`) is one day more lenient between 17:00 and 24:00 PDT.
   - The failure meant CoastWatch **could not confirm** that no newer run existed. At 05:51Z, ERDDAP showed a newer run (nowcast valid 10-11; `history` says "2026-10-12: …"; lead 3 valid 10-14). So the badge certified a run as current that upstream had already superseded.
   - The web already has the stricter rule in one place: `W:lib/health.ts:12` treats a failed source as at least stale. The panel badge, `ForecastPanel.tsx:34`, `MyCoast.tsx:178,306` and `opening.ts:43,57` do not apply it.

### Proposed single rule (no manifest schema change; uses the existing `outcome`, `last_attempt_at` and `last_success_at`)

> A product is **Current** only if (a) its basis date is within `current_max_age_days` in the **Pacific**
> calendar, **and** (b) the latest update attempt for that product succeeded (`updated`, `unchanged`,
> or `partial` with no error matching that product). If (a) holds but (b) fails, the state is
> **Unconfirmed**: amber, and ranked like Stale for opening-view and worst-state logic. Otherwise
> the state is Stale or Historical by age, as now.

Implement it once (e.g. `classifyWithStatus(policy, time, status, product, now)` in `freshness.ts`). Use it in LayerDock, ForecastPanel, MyCoast, opening.ts, health.ts, SourceTable and observations (`carried_forward` = (b) fails). In parallel, fix the pipeline notes and `health.py` to state and use the Pacific calendar, and stamp `port_intel`/`cdfw_ports` dates with the Pacific date, or better, with their oldest *input* date.

**Wording (one template, every panel):**
- Badge: **`Not confirmed · issued Oct 11`** (observations: `Not confirmed · observed Oct 10`).
- Line beside it: **`Couldn't reach NOAA at 5:42 PM PDT, so a newer run may exist. Showing the last run we received (checked 8:29 AM PDT), with its own dates.`**

This reuses the tone of the station message "newer samples may exist" (`StationHeader.tsx:107-108`). It never says "Current" next to "failed", and it never implies the data are wrong.
